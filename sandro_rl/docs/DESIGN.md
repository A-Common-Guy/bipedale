# sandro_rl design notes

How the training environment is built, why, and how far its results can
be trusted. Each number is either measured in this repository (the command
that produced it is named) or cited, either to [RESEARCH.md](RESEARCH.md) or
to the ROS stack's own notes,
[SIM_TO_REAL.md](../../ros2_ws/src/sandro_bringup/docs/SIM_TO_REAL.md).
That file is cited below as "S2R" with a line number.

All measurements were taken on one machine: an RTX 5070 Ti (16 GB), MuJoCo,
MJX and MuJoCo Warp 3.16.0, warp-lang 1.18.0 and jax 0.11.2 (CUDA 13);
`uv.lock` has the exact versions.

## 1. Layout and data flow

```text
ros2_ws/src/...                 (read, never written)
  sandro_description/mjcf/scene_ros2.xml, robot_ros2.xml   the generated model
  sandro_description/config/sim_identified.yaml            identified mass, friction, payload
  sandro_bringup/config/controllers.yaml                   rates, limits, gains, command shaping
  sandro_bringup/config/sandro_real_overrides.yaml         per-robot overrides
  sandro_bringup/launch/sandro.launch.py                   latency emulation defaults
  sandro_sim/tools/closed_loop.py                          WBC closed-loop harness (evaluation)
        |
        v
sandro_rl/sources.py   reads all of the above, hashes them (fingerprint)
sandro_rl/robot.py     loads the MJCF, checks the model contract
sandro_rl/env.py       batched GPU environment (MJX, impl=warp)
sandro_rl/train.py     PPO + curriculum; checkpoints carry config and fingerprint
sandro_rl/export.py    ONNX + policy.json (the deployment contract)
sandro_rl/evaluate.py  CPU MuJoCo, full latency emulation, side by side with the WBC
sandro_rl/consistency.py   CPU MuJoCo vs GPU backend check
```

Nothing in `ros2_ws/` was changed. Changes I suggest there are listed in
section 11.

## 2. Backend choice

The candidates were MJX's JAX backend, MuJoCo Warp through MJX
(`impl="warp"`), and Isaac Lab. Isaac Lab would need Isaac Sim, a very large
SDK that I was asked not to install without asking. It also needs the
five-bar closed loops re-expressed for PhysX, which requires a higher solver
iteration count for loops (RESEARCH.md, Isaac Lab entry). MuJoCo Warp runs
the exact MJCF that the ROS simulation runs, so model fidelity carries over
for free. Only the GPU-side Python wheels were needed: no driver or toolkit
change.

`uv run python -m sandro_rl.bench` measures physics steps per second. The
unpowered robot starts from the stand keyframe and tips over, so both tyre
and body contacts are exercised. There is no policy in the loop.

| Backend | 1024 worlds | 4096 | 8192 |
| --- | --- | --- | --- |
| MJX-Warp, graph mode `warp` | 2.24M | 4.58M | 5.18M |
| MJX-Warp, graph mode `warp_staged` (used) | 1.11M | 2.32M | 2.60M |
| MJX-JAX, body meshes not colliding | 0.30M | 0.62M | 0.74M |
| CPU MuJoCo, one thread | 89.7k (one world) | | |

The figures are physics steps per second, from `docs/bench.json`. The
compile times printed by the benchmark are with Warp's kernel cache warm.
A cold first run spends minutes compiling kernels.

These are the reasons for the choice:

- **MJX-JAX cannot run the model as it is.** `put_model` rejects collisions
  between the tyre cylinders and the body meshes, so its numbers above are
  for a copy with the body meshes taken out of collision. It cannot run
  obstacles either: there is no cylinder–box or cylinder–heightfield
  collision (RESEARCH.md, bottom line). Even on the simpler model it is
  3.5–7× slower than Warp.
- **Graph mode.** MuJoCo Warp's default CUDA-graph mode (`warp`) caches one
  graph per buffer-address set. In PPO training at 8192 environments it ran
  out of GPU memory after about 10 iterations. `jax` mode failed with
  `CUDA_ERROR_NOT_SUPPORTED` (a child graph node). `warp_staged` copies
  through fixed staging buffers and trains stably. In raw physics it reaches
  half the speed of `warp` (table above). In the full training loop it runs
  at 157k environment steps/s, against 245k with `warp` for the iterations
  that `warp` survived. It is set in `configs/base.yaml`
  (`env.graph_mode`).
- **End-to-end training rate.** `flat_tracking` trained at 153.7k
  environment steps/s averaged over the whole run, compile included (16.7 s).
  That is 1.84M physics steps/s, at 4 physics steps per control cycle and 3
  control cycles per policy step (`policies/flat_tracking/train_summary.json`).
  The `agile_obstacles` task, with 16 obstacle boxes per world and larger
  contact buffers, ran at about 125k.

## 3. Model sync

### What is read from where

| Quantity | Source | Read by |
| --- | --- | --- |
| Kinematics, inertias, contacts, physics step 1/1200 s | `mjcf/scene_ros2.xml` (generated by `sync_model.py`) | `robot.RobotSpec.load` |
| Identified mass, payload, friction, IMU mount | `sim_identified.yaml`, already in the MJCF; the file is hashed and its tyre friction cross-checked | `robot.check_contract` |
| Control rate 300 Hz, joint order, leg drive kp 12 / kd 0.5 | `controllers.yaml` | `sources.controller_parameters` |
| Torque limits: legs 3 Nm, wheels 6 Nm | `controllers.yaml` `limits` | same |
| Command limits and shaping: 0.5 m/s, 1.5 rad/s, 1 m/s², 0.15 s yaw lag, 0.05 m/s height rate, height 0.14–0.185 m | `controllers.yaml` `drive`, `tasks.height` and the robot overrides | same |
| IMU mounting offset, fall angle 1.0 rad | overrides and `controllers.yaml` `safety` | same |
| Latency defaults: IMU 10 ms at 200 Hz, joints 1 ms at 200 Hz staggered, command 1 ms | `sandro.launch.py` `DeclareLaunchArgument` defaults (parsed with `ast`) | `sources.launch_latency` |

Task configs write `ros` where a value comes from the stack. No number is
duplicated.

### The model contract

`robot.check_contract` raises `ModelContractError` when the model differs
from what the environment handles. It checks:

- the six joint names and their order;
- one direct motor per joint (gear 1, ctrl size 6);
- the `stand` keyframe;
- the IMU site and its sensors;
- the tyre geoms: condim 4, and friction equal to `sim_identified.yaml`;
- the 1/1200 s physics step dividing the 300 Hz control period.

### CPU against GPU consistency

`uv run python -m sandro_rl.consistency` runs four seeded open-loop torque
sequences. Each is the hold torque plus sinusoids of 0.1–0.3 × the torque
limit at 0.5–4 Hz, run for 0.2 s (240 physics steps), in CPU MuJoCo and in
MJX-Warp from the same state. That state is the keyframe after landing:
0.3 s under leg PD, because the keyframe itself is slightly airborne. Two
checks follow:

- **One step:** every 20 steps the GPU is stepped once from the CPU state.
  The tolerance is |Δqvel| ≤ 2e-3. Measured: 6.4e-5 (6e-5 to 8e-5 across
  development runs).
- **Rollout:** the whole 0.2 s horizon. A fixed tolerance is not meaningful
  here, because the model amplifies float differences on its own. The passive
  five-bar links have armature 1e-5, and the robot tips over in open loop.
  The check therefore compares the GPU difference with the spread of CPU
  runs perturbed by 4e-5 relative qvel noise per step, times 3, plus a floor
  (legs and wheels 2e-3 rad, base 2e-4 m). The current model gives:

  | Quantity | GPU − CPU | CPU noise spread | Tolerance |
  | --- | --- | --- | --- |
  | leg joints | 0.049 rad | 0.032 rad | 0.096 rad |
  | wheel angles | 0.108 rad | 0.086 rad | 0.261 rad |
  | base position | 2.9 mm | 2.6 mm | 7.9 mm |

  So the GPU's difference is the size of float noise. Earlier development
  runs, with other seeds and start states, gave legs 0.05–0.125 rad and
  wheels 0.1–0.17 rad.

The contract runs first. `tests/test_consistency.py` copies the MJCF folder
and makes seven alterations. Each one makes the check fail, and the
unaltered model passes:

- a renamed joint;
- gear 2;
- a missing actuator;
- a removed keyframe;
- tyre condim 6;
- tyre friction 0.6, which `sim_identified.yaml` does not contain;
- physics step 1 ms.

### Fingerprint

`sources.fingerprint()` is a SHA-256 over these files:

- the scene and robot MJCF and their mesh files;
- `sim_identified.yaml`, `controllers.yaml` and the overrides;
- `sandro.launch.py`.

It is stored in every checkpoint (`meta.json`) and in `policy.json`.
`checkpoint.load`, `export` and `evaluate` warn and print the changed files
on a mismatch. They do not refuse: a changed comment also changes the hash.

### Refresh procedure after `sync_model.py sync`

```bash
cd sandro_rl
uv run python -m sandro_rl.consistency     # contract + CPU/GPU check; must pass
uv run pytest -m "not gpu"                 # contract tests on altered copies
uv run pytest                              # all tests, observation contract included
```

What to do next depends on the result:

- **The contract fails** (renamed joint, new actuator, changed contact
  type): update `sources.py` (`JOINTS`, `TYRE_SUFFIX`) and `robot.py`
  deliberately. The failure message names the check.
- **The contract passes but the fingerprint warns:** the physics changed.
  Retrain, or fine-tune from the old checkpoint with `--resume`. Then
  re-export and re-evaluate. An old policy can be evaluated against the new
  model to measure how much the change matters.
- **Only rates, limits or shaping changed:** export again, so `policy.json`
  carries the new limits, and run the evaluation.

## 4. Environment

### Timing

| Step | Rate | Source |
| --- | --- | --- |
| Physics | 1200 Hz | MJCF timestep |
| Drive MIT law | every physics step, on the true joint state | S2R l.43–45; `MitDrivePlugin` |
| Control cycle, sensor sampling | 300 Hz | controllers.yaml `update_rate` |
| Policy | 100 Hz, every 3rd control cycle | config `env.policy_rate_hz` |

I chose a policy rate of 100 Hz because the drive-side PD makes the legs
fast without a fast policy, as on Ascento with its low-level PD (RESEARCH.md
§1). It also gives a 3× cheaper rollout. The policy's MIT frame is held for
three control cycles. `policy.json` states the rate so a deployment can
check it.

### Latency emulation

The GPU environment keeps a ring buffer of raw sensor channels at physics
rate: quaternion, gyro, accelerometer, six joint positions and six joint
velocities. `latency.sample_time` follows the ROS emulation's model (S2R
l.47–52), and `evaluate.DelayLine` ports it line for line on the CPU side.
Each channel has a sample clock (rate and phase), and the controller sees
the last sample older than the transport delay. Commands are applied after
the command delay, at physics-step resolution. The CPU evaluation instead
runs the `DelayLine` and `DriveBus` ports and the controller manager's
wake-up rule, all taken from `closed_loop.py`. Run against the same command
sequence, the WBC numbers it produces are the ones `closed_loop.py` itself
reports.

### Actions: the MIT interface

The policy outputs 6 values in [−1, 1], in joint order. Each becomes one MIT
frame per drive, `tau = kp (q_ref - q) + kd (v_ref - v) + tau_ff`, clipped
to the controllers.yaml torque limits:

- **Legs:** `q_ref = stand_q + 0.5 rad × a`, clipped to the joint range,
  with kp 12 and kd 0.5 from controllers.yaml. This is the same in-drive PD
  the WBC uses (`tasks.legs.pd_in_drive`, S2R seventh comparison).
- **Wheels:**
  - `velocity` mode: `v_ref = 20 rad/s × a`, kd 0.4 (the default).
  - `torque` mode: `tau_ff = 3 Nm × a`.

Velocity mode follows the hardware wheel-leg recipe (RESEARCH.md bottom
line). It also lets the drive's own loop reject the 0.2 Nm Coulomb friction
per wheel (S2R l.139) without the policy seeing it through the delay.

### Commands

The command is (forward speed, yaw rate, body height), resampled every
2–5 s. 20 % of commands are all zero, and each component is zeroed with
probability 0.25. The height changes in half the resamples. The policy
observes the **shaped** reference: rate-limited acceleration, first-order
yaw lag, rate-limited height, with the WBC's parameters from
controllers.yaml. Both controllers therefore follow the same reference from
the same `/cmd_vel`. `interface.PolicyInterface.shape` implements this for
deployment.

`agile_terrain` adds a fourth component, the body roll target, for
animation (section 8). Each resample draws it within ±0.3 rad, or zero with
probability 0.4. It is clipped to what both legs can reach at the current
height, |roll| ≤ atan(2·min(h − 0.07, 0.195 − h)/track width), and is
rate-limited to 0.6 rad/s. The tracked roll is this target minus the
coordinated-turn lean. Roll and height are soft objectives: tracking
kernels and a quadratic penalty, and no constraint holds them to the target.

### Observations

The actor sees one frame of 25 values per policy step, and stacks the 4 most
recent frames (100 inputs):

- projected gravity (3), from the delayed IMU quaternion, with the known
  mounting roll removed as `tasks.roll.imu_offset_rad` does in the WBC. In
  training that is the simulated mount (`sim_identified.yaml` `imu_mount`);
  on the robot it is the `rl_*` override's `observation.imu_offset_rad`;
- gyro (3, ×0.25);
- leg joint positions relative to `stand_q` (4);
- leg velocities (4, ×0.1);
- wheel velocities (2, ×0.05);
- previous action (6);
- normalised shaped command (3; 4 with the roll target).

Wheel angles are left out because they are meaningless. Base linear velocity
is left out because the robot has no sensor for it. The accelerometer can be
switched on (`observation.accelerometer`) but is off: the gravity vector
already comes from the BNO085's fusion.

The critic sees 68 values (asymmetric actor-critic, Pinto 2017; Ascento RL,
RESEARCH.md §1). That is the actor's current frame plus true gravity, gyro,
joint state, base velocity, leg heights, fore-aft leg offsets, wheel
clearance, the push force and 8 normalised model parameters.

`tests/test_observation_contract.py` checks that `PolicyInterface`, the numpy
code the CPU evaluation and the deployment use, produces bit-for-bit the
frame, MIT frames and command shaping of the GPU environment. It also checks
the mirror maps.

### Rewards and constraints

Rewards use exponential tracking kernels and quadratic regularisers, as in
legged_gym and Playground (RESEARCH.md §5). Each term is multiplied by the
policy period. The weights for `flat_tracking` are:

| Term | Weight | Note |
| --- | --- | --- |
| alive | 1 | |
| exp(−((v − v_ref)/0.15)²) | 2 | true forward speed in the heading frame |
| exp(−((ω − ω_ref)/0.35)²) | 1 | world yaw rate |
| exp(−((h − h_ref)/0.012)²) | 1 | mean leg height from the kinematics |
| (roll + lean)² | −20 | lean = atan(v ω / g), the coordinated-turn roll |
| pitch² | −2 | |
| pitch rate² | −0.05 | |
| vertical velocity² | −2 | |
| (right − left fore-aft leg offset)² | −200 | keeps the legs together |
| action rate², action acceleration² | −0.02, −0.01 | |
| leg torque², wheel torque² | −0.002, −0.01 | mean over physics steps |
| leg joint velocity² | −0.0005 | |
| termination | −200 | |

Hard limits use Constraints as Terminations (Chane-Sane 2024, RESEARCH.md
§4): each violated constraint raises the episode's termination probability,
up to 0.25 per step, in proportion to the violation over its slack. The
constraints are:

- leg torque above the 3 Nm limit;
- five-bar stretch above 0.97 (1 is the singular, fully stretched pose);
- joint range with a 0.1 rad margin;
- height outside the commanded range by more than 8 mm;
- tilt beyond 0.45 rad;
- a wheel lifting by more than 1 cm.

An episode terminates outright at 0.8 rad tilt (the WBC declares a fall at
1.0) or with the IMU below 0.17 m.

PPO adds the mirror loss of Mittal 2024 (weight 0.5). A left–right mirror
of the robot swaps the legs, flips the lateral and yaw signs and keeps the
joint signs, because the joints are mirrored in the URDF. The mirror maps
are tested to be involutions.

### Kinematics of the five-bar legs

`kinematics.py` is the closed-form forward kinematics (base 0.09 m, upper
0.08 m, lower 0.13 m, read from the MJCF). At the neutral offset the
reachable leg height is 0.022–0.199 m at stretch ≤ 0.97. The static leg
torque stays at or below 1.07 Nm between 0.08 and 0.2 m. So the ROS height
range 0.14–0.185 m uses a small part of the linkage. The `agile_obstacles`
task widens it to 0.11–0.19 m (section 8).

The ranges are resampled each episode (latency, sensors, drives) or drawn
once per environment for the whole run (model fields, the Playground
pattern). Each one is centred on, or brackets, an identified or measured
value.

## 6. Training

The training algorithm is PPO in JAX (`ppo.py`), in the style of rsl_rl:

- adaptive learning rate on a KL target of 0.01;
- 8192 environments × 24 steps per iteration, 5 epochs, 4 minibatches;
- γ 0.99, λ 0.95;
- ELU MLPs: actor 256-256-128, critic 512-256-128;
- running observation normalisation, which is exported with the policy;
- the symmetry loss.

Curricula are listed as `curriculum.stages` in the task config. Each stage
sets dotted config keys from a given iteration. When a stage starts, the
environment and the randomised model batch are rebuilt; networks,
normalisers and optimiser carry over.

### Determinism

Everything is seeded: JAX keys, numpy, the per-environment randomisation,
and the CPU evaluation's noise. The CPU evaluation is bit-exact
(`tests/test_determinism.py`). The GPU rollout is not, because MuJoCo Warp's
constraint solver accumulates with float atomics. Two runs with the same
seed agree to about 6e-7 after one step. After one PPO iteration 0.05 % of
the weights differ, by at most 2.7e-3, because Adam amplifies tiny gradient
differences. The test asserts a relative parameter difference below 1e-3,
and also that a different seed differs.

Warp's `DeterministicMode.RUN_TO_RUN` was tried and rejected:

- compiling one reset took 539 s;
- the difference grew (0.025), because the deterministic contact ordering
  changed the floating-point summation order rather than fixing it.

## 7. Evaluation

`evaluate.py` runs the exported ONNX policy in CPU MuJoCo, with onnxruntime
at 100 Hz inside the 300 Hz loop, using the code `closed_loop.py` uses:

- the `DelayLine` and `DriveBus` emulation;
- the controller manager's wake-up rule;
- IMU noise and `/cmd_vel` published at 20 Hz;
- the 3 s settle, pushes and the fall rule.

It writes `drive_test.py`-compatible CSVs and summarises them with the same
per-phase metrics as `compare_runs.py`. It also runs the WBC through
`closed_loop.py` on the same scenario and latency profile. Three latency
profiles are used:

- `nominal`: the launch defaults.
- `uart_imu`: the IMU at 30 Hz, the measured hardware rate (S2R l.469).
- `worst`: IMU at 30 Hz with 25 ms delay, joints 5 ms, commands 3 ms.

The `truth_*` columns are measured from the simulator state. They exist
because the controllers' own estimates differ: the WBC estimates speed from
the wheels and the policy has no speed estimate at all.

### flat_tracking against the WBC

`uv run python -m sandro_rl.evaluate policies/flat_tracking --compare`
writes the full table to `policies/flat_tracking/eval/comparison.md`, for
three scenarios (closed_loop's `hardware`, `default`, `push`) × three
profiles. Survival:

| Scenario | nominal | uart_imu | worst |
| --- | --- | --- | --- |
| hardware (5 phases, 0.2 m/s, 0.6 rad/s turn) | both complete | both complete | policy completes, WBC falls |
| default (11 phases, 0.3 m/s, 1 rad/s spin, height changes) | both complete | policy completes, WBC falls in phase 1 | policy completes, WBC falls |
| push (8 N shoves) | both complete | both complete | policy completes, WBC falls |

The WBC's fall on `default/uart_imu` is a known, pre-existing result.
`closed_loop.py check` fails that gate in the same way (S2R l.489–491,
l.518–519).

pitch about its phase mean (as `compare_runs.py` computes it). Speed error is
`compare_runs.py`'s `vel_err_rms`: wheel odometry plus pitch rate against the
shaped reference, computed the same way for both controllers. The full table
is in the file.

| --- | --- | --- | --- |
| standing (0) | pitch RMS, rad | 0.046 | **0.023** |
| standing (0) | speed error RMS, m/s | **0.027** | 0.072 |
| driving 0.2 m/s (1) | pitch RMS, rad | 0.040 | **0.002** |
| driving 0.2 m/s (1) | speed error RMS, m/s | 0.072 | **0.050** |

| turn (3) | yaw rise time, s | **0.12** | 1.02 |
| all | wheel torque RMS, Nm | 0.24–0.46 | 0.22–0.44 |
| all | leg effort RMS, Nm | 0.79–0.99 | 0.78–0.93 |

The truth speed comes from `closed_loop.cpp` (`Sim::truth`). It is the
speed of the torso body's origin, `hypot(qvel[0], qvel[1])`. That origin is
the CAD origin, 0.35 m from the axle midpoint horizontally and 0.17 m above
it. While turning it therefore adds about ω × 0.35 m: 0.21 m/s at
0.6 rad/s. Pitch motion adds to it as well. The truth speed errors in the
turn phases mean nothing for either controller and are left out above.
Measured at the axle midpoint (`diag_truth_forward_m_s`, policy only), the
policy drove 0.172 m/s in the 0.2 m/s turn of `hardware`, and 0.270 m/s in
the 0.3 m/s spin of `default`. The WBC's recordings have no axle speed
column. Section 11 proposes the fix.

**Where the policy is worse:**

- **Pitch.** Its body pitch RMS is about twice the WBC's in every standing
  phase (0.046–0.066 against 0.023–0.039 rad). Its mean standing pitch is
  also +0.06 to +0.09 rad, against −0.003 to +0.005 for the WBC. In the last
  2 s of the standing phases its pitch standard deviation is 0.017–0.044 rad,
  against 0.004–0.025. With a pitch weight of only −2, pitch is nearly free
  in the reward. A wheeled inverted pendulum can stand at any pitch for which
  it shifts the legs under the CoM, so a tilted body costs it almost nothing.
  `flat_level` (section 8) tests this explanation.
- **Steady driving.** It drives with more pitch and less precise speed than
  the WBC at 0.2 m/s.
- **Torque under worst-case latency.** It survives the `worst` profile with
  a calm body (pitch RMS 0.02–0.05), but spends 0.8–1.8 Nm RMS of wheel
  torque doing so, against 0.2–0.5 at nominal latency, with up to 6 %
  wheel-velocity sign flips. On the robot that is heat and audible chatter.

**Where the policy is better:**

- It survives every latency profile.
- Yaw tracking is 3× more accurate and 8× faster to rise.
- Standing station-keeping is better: speed error 0.027 against 0.072 m/s.
  The WBC drifts ±0.1–0.2 m/s with its 0.3–0.4 Hz friction sway
  (S2R l.499–504).

The plot `policies/flat_tracking/eval/hardware_nominal.png` shows the traces.

### agile_obstacles: using the legs

The WBC uses the five-bar legs as a slow posture and height actuator inside
0.14–0.185 m. The linkage reaches 0.022–0.199 m (section 4). It is strong
enough there: the static leg torque is at most 1.07 Nm of the 3 Nm limit.
The legs are also fast with the drive-side PD: 72 ms response at kp 12
(S2R l.410–413). `configs/agile_obstacles.yaml` asks the policy to use this:

- commands up to 1.0 m/s and 3.0 rad/s, twice the controllers.yaml limits;
- 2 m/s² acceleration and a 0.15 m/s height rate;
- heights from 0.11 to 0.19 m;
- 16 randomly placed planks per world, 5–25 mm high, 4–30 cm deep and
  0.2–1 m wide;
- wheel velocity targets up to 25 rad/s;
- tighter tracking kernels and a stronger pitch penalty (−10);
- a three-stage curriculum. At iterations 0, 300 and 700 the sampled
  command range is 40 %, 70 % and 100 %, and the plank heights are
  2–8 mm, 4–16 mm and 5–25 mm.

Ascento climbed 15 cm steps blind with a similar recipe (RESEARCH.md §1).
The 0.11 m lower bound is my choice of margin, not a measured limit.

The run took 38.7 minutes for 295M environment steps: 127k env steps/s and
1.53M physics steps/s, compile included. At the end, the training tracking
errors were 0.107 m/s, 0.106 rad/s and 5.7 mm, with 0.005 falls per 1000
episode-steps (`policies/agile_obstacles/curves.png`).

**These plank results are invalid.** Only the first plank of the course
collided; the rest were drawn but not solid, and the same was true of the
training planks. The planks were static world geoms, moved after compilation

where they were compiled. The policy was therefore trained on flat ground,
and the course below crossed one real plank. `agile_terrain` replaces it
(below), with obstacles as mocap bodies and a test that they carry the
wheels (`tests/test_terrain.py`). The table is kept as a record.

### agile_terrain: obstacles that collide, slopes, kicks, roll and height

`configs/agile_terrain.yaml` replaces `agile_obstacles`. Relative to it:

- **Obstacles are mocap bodies** (`terrain.py`). Each world has 12 planks
  and 4 hills; a hill is a plateau box between two ramp boxes. They are
  compiled at their largest height and sunk into the floor to the sampled
  height, and their poses are written to `mocap_pos`/`mocap_quat` at every
  reset. So the layout is new every episode, and each world's is different.
  Warp does not drop contacts between two mocap bodies, so obstacle geoms
  have `contype` 2 and `conaffinity` 1: they collide with the robot and not
  with each other or the floor. Rewards and terminations that need the ground
  height use an analytic one, the highest box top under the point.
  `tests/test_terrain.py` checks that a plank placed at run time lifts the
  wheels by its height, 20 mm for 20 mm on the CPU and in Warp. It also
  checks that the analytic height matches `mj_ray` and that every course
  obstacle collides where it is drawn.
- **Disturbances.** Pushes go up to 25 N fore-aft, 12 N lateral and 15 N
  vertical, with torque kicks of 1 Nm about the heading (roll) and about z.
  They last 0.05–0.25 s and come every 2–6 s. The critic sees all five
  components.
- **Roll and height as commands** (section 4, Commands). Height ranges over
  0.09–0.19 m and roll over ±0.3 rad, clipped to what both legs can reach.
  Neither is a constraint, only a reward: tracking kernels with sigmas
  0.03 m and 0.06 rad, and a −5 roll penalty.
- **Curriculum.** At iterations 0, 400 and 900: commands at 40, 70 and 100 %
  of their range; planks 2–10, 4–20 and 5–30 mm; hills 0–3, 1–6 and
  2–10 cm; pushes rising to the values above. Stages accumulate, so the last
  stage restates the full values.

**Training history.** The policy took three runs:

| Run | Iterations | Change |
| --- | --- | --- |
| `agile_terrain_v0` | 1200 of 2000 | Diverged at iteration 1220 |
| `agile_terrain_v1` | +800 | Resumed from v0's checkpoint 1200 at full difficulty |
| `agile_terrain_v2` | +500 | Height kernel widened |

- **v0's divergence:** one world's simulation diverged, and its NaN
  observation reached the shared observation normaliser, which poisoned
  every world. `env.step` now terminates a world whose state is non-finite
  or whose |qvel| exceeds `termination.max_qvel` (200). It zeroes that
  world's observation and gives it the termination reward.
- **v1's resume:** run with an initial learning rate of 1e-4. At the
  config's 1e-3, the fresh optimiser's first step reached a KL of 144.
- **v2's height kernel:** the height sigma went from 0.015 to 0.03 m and
  its weight from 1 to 2. With the narrow kernel the reward was flat beyond
  about 4 cm of error. Commanded down to 0.093 m, the v1 policy *rose* to
  0.177 m.

Total: 2500 iterations, 1.26 G env steps, 75 minutes. At the end the
training errors were 0.19 m/s, 0.22 rad/s, 15 mm in height and 0.02 rad in
roll, with 0.09 falls per 1000 steps, all at full difficulty.

**The course** (`evaluate --scenario course --course`, CPU MuJoCo, nominal
latency) has planks 10, 15, 20 and 25 mm high at 1.0–3.4 m. They are
followed by an 8 cm hill with 10° ramps and a 0.6 m plateau, centred at
5 m. The policy completes it (`course.mp4`, `eval/course_frames.png`,
`eval/course.png`). Positions below are dead-reckoned from axle speed and
yaw rate:

| Phase | Command | Achieved |
| --- | --- | --- |
| 1 | 0.5 m/s | 0.40 m/s, over the 10 mm plank |
| 2 | 0.8 m/s | 0.69 m/s, over the 15, 20 and 25 mm planks and up the hill; stops at x = 5.3 m, on the plateau. Pitch peaks at 0.37 rad |
| 3–4 | stop, then spin at 2.5 rad/s on the plateau | 2.48 rad/s |
| 5 | 0.6 m/s, 90° to the course | 0.58 m/s, off the side of the hill's plateau and down |

**The expressive sequence** (`--scenario expressive`, `expressive.mp4`,
`eval/expressive_frames.png`, `eval/expressive.png`) lowers the body, rolls
it both ways, crouches, rises and then drives while rolled. Roll follows:
0.25–0.26 rad for ±0.3 commanded at 0.13 m, and 0.22 for ±0.25 while
driving at ±0.3 m/s. The RMS error is 0.03–0.05 rad, including the
transitions. A coordinated turn at 0.4 m/s and 1 rad/s leans the body by
0.05 rad into the turn, as the reward asks.

**Where it is worse:**

- **Height follows only within about 0.12–0.18 m.** Commanded to 0.093 m,
  the legs stop at 0.122 m; commanded to 0.19 m, they stop at 0.177 m. While
  rolling at 0.13 m the mean leg height rises to 0.153 m. I checked and ruled
  out these causes:
  - kinematics: the joints are far from their limits at 0.09 m;
  - self-collision;
  - torso clearance: 0.19 m at a 0.09 m leg height;
  - the IMU-height termination: the IMU is 0.30 m above the ground at
    0.09 m.

  The cause is open; the next things to try are listed in section 10.
- **It rocks slowly while standing**, with pitch swinging between 0 and
  0.1 rad. The pitch penalty (−10) is a quarter of `flat_level`'s.
- **It undershoots speed** by 14–20 % in steady state, like
  `agile_obstacles`.
- **Standard scenarios** (`eval/comparison.md`): it completes all nine
  scenario/profile runs, and the WBC falls in four. In the 10 s push test at
  nominal latency its truth pitch RMS is 0.047 rad against the WBC's 0.023.

### jump: wheels off the ground on command, at 10 Nm

`configs/jump.yaml` is `agile_terrain` (same terrain, pushes, roll and
height commands) plus a jump event. It is a first policy to build the more
dynamic tasks on; its torques are past what the hardware has been run at, so
it is not expected to transfer before the system identification is done.

- **Torque limits** go to 10 Nm on legs and wheels (`action.torque_limit_nm`,
  the hardware plugin's `hard_effort_limit_nm`), against 3 and 6 Nm from
  controllers.yaml for the other policies. The CaT leg-torque limit is
  9.5 Nm. Legs use kp 20, kd 0.6 and an action scale of 0.8 rad.
- **The jump event.** Every 2–5 s a jump window of 0.8 s opens with a target
  height of 2–8 cm (curriculum: 1–3, 2–5, then 2–8 cm at iterations 0, 400
  and 900). The actor sees two more inputs, `[height / 8 cm, time left /
  0.8 s]`, zero outside the window, so the observation grows by 2 per frame
  (112 actor, 74 critic).
- **Rewards in the window:** the lower wheel's clearance up to the target
  (weight 40), upward base speed (2), and a quadratic penalty above the
  target (−2000). Height tracking, the vertical-speed penalty and the
  wheel-lift constraint are off during the window and 0.3 s after it.
- **The evaluation** gives a jump the sixth field of a scenario phase,
  started on its rising edge (`--scenario jump`), and records the lower
  wheel's clearance above flat ground (`diag_truth_wheel_clearance_m`).

Training took 74.6 minutes for 2500 iterations (491.5M env steps, 109.8k
env steps/s, 1.32M physics steps/s), with no divergence. At the end it falls
0.35 times per 1000 policy steps, against `agile_terrain`'s 0.08.

**What it learned** (`jump.mp4`, `eval/jump_frames.png`, `eval/jump.png`):
in every window it hops three times, tucking the legs to 0.10 m between
hops, and lands back at its 0.17 m height within 0.2 s of the window's end.
It does this standing and at 0.5 m/s:

| Phase | Target | Hops | Peak clearance | Peak leg / wheel torque |
| --- | --- | --- | --- | --- |
| standing | 3 cm | 3 | 66 mm | 8.4 / 5.0 Nm |
| standing | 5 cm | 3 | 84 mm | 7.7 / 5.2 Nm |
| standing | 8 cm | 3 | 127 mm | 7.3 / 7.1 Nm |
| 0.5 m/s | 5 cm | 3 | 107 mm | 7.4 / 6.3 Nm |
| 0.5 m/s | 8 cm | 3 | 126 mm | 7.2 / 6.2 Nm |

It completes all nine standard scenario/profile runs (`eval/comparison.md`;
the WBC falls in three, the `worst` latency profile).

**Where it is worse, and what to change:**

- **It hops three times instead of jumping once.** The reward pays for
  clearance at every step of the window, and short hops keep the wheels up
  for more of it than a single flight of about 0.3 s. A single jump needs a
  reward on the flight's apex, or a window that closes at the first
  touchdown.
- **The height command shapes it only loosely.** It overshoots small
  targets (66 mm for 3 cm) despite the overshoot penalty; the 8 cm target
  is met. Rewarding the apex against the target would fix both.
- **It falls four times as often as `agile_terrain` in training.** The
  jumps are on the same terrain and pushes, and landings on plank edges are
  the likely cause (not traced).
- **The torque is 10 Nm on every drive, and the landings are not checked
  against the hardware.** The drives' peak current, the five-bar links'
  strength and the tyres' landing impact are not modelled. The deployment
  controller has no jump input yet (section 9).

### Refit to the weighed robot

On 2026-10-21 the model changed from the CAD masses to the weighed ones
(`sim_identified.yaml` `masses`): 4.825 kg against 3.40 kg, wheels 170 g
against 58 g, and the loaded tyre radius 0.0672 m against 0.0742 m. The
controllers' model, wheel radius included, followed. The contract and the
CPU/GPU check pass on the new model.

**IMU roll correction, fixed with the refit.** Training had taken the
observed roll correction from the robot overrides'
`tasks.roll.imu_offset_rad`. That value was re-identified to +0.016 rad for
the SPI6 mounting, while the simulated IMU stayed mounted at −0.049. The
first `jump` training therefore saw a horizon tilted by 0.065 rad, which it
would have held on the robot. The correction is now the simulated mount

refit below starts from the committed checkpoints with that fix: three of
them were trained before the re-identification, and `jump` relearns the
horizon in its refit.

chose that checkpoint on it; the per-checkpoint sweep made with it is
withdrawn.

`policies/step_climb` (v1, checkpoint 1200), 5 seeds, nominal latency:

| --- | --- | --- | --- | --- |
| none (`--heading-hold 0`) | 7 / 20 | 3 cm on 5 seeds, 4 cm on 2 | 0 / 5 | 0 / 5 |

With the operator steering it stays on the line and stops at the 4 or 5 cm
plank, 1.8–2.8 m along the course. Without, it turns after the first
crossing and drives past the others beside them, which is what
`steps.mp4` shows.

- **The legs are split fore and aft.** In v1 and in `jump` the two legs'
  fore-aft offsets differ by 60–75 mm while standing (`agile_terrain`:
  about 1 mm). One wheel ahead of the other makes the robot statically
  stable in pitch, which pays under the pitch penalties and survives
  pushes; the `leg_symmetry` penalty (−200 per m², 0.7 per second at 60 mm)
  is too small to stop it. It is an exploit, not a gait anyone asked for.
  `constraints.leg_split` (CaT, here 20 mm with 30 mm slack) removes it, as
  v2 shows.
- **Why v2 stops.** Rolling a wheel up an edge of height h takes a tyre
  friction of at least tan θ, with cos θ = (r − h) / r: about 1.5 at 3 cm and
  2.2 at 4 cm for the 67 mm tyre, against 0.5–1.2 in training. A blind robot
  gets up a step only on momentum or by unloading the wheel with the legs.
  v1 did it from the split stance, one wheel at a time; with the legs held
  together and steep faces that punish a failed try, v2 learnt not to try.
  Commanding a jump in front of the plank does not help: it reverses away
  from the face after landing.
- **Hop on command** (`configs/step_climb_hop.yaml`, run `step_climb_hop_v1`,
  1500 iterations from v2, 45.6 min). In training the jump request also fires
  whenever the ground 0.1–0.4 m ahead rises by more than 1.5 cm, with a
  target of the rise plus 2 cm. `evaluate.py --hop` plays an operator who
  does the same from rays against the course. The legs stay together
  (≤ 5 mm). With heading hold 2 and hops, 5 seeds:

  | Checkpoint | 600 | 800 | 1000 | 1100 | 1200 | 1300 | 1400 | 1500 |
  | --- | --- | --- | --- | --- | --- | --- | --- | --- |
  | planks / 20 | 8 | 5 | 5 | 3 | 11 | 2 | 6 | 10 |
  | falls on the steps course / 5 | 5 | 5 | 5 | 5 | 4 | 5 | 3 | 5 |
  | onto the curb / 5 | 3 | 1 | 3 | 0 | 0 | 4 | 0 | 2 |
  | falls on the curb course / 5 | 1 | 0 | 0 | 0 | 0 | 1 | 0 | 0 |

  It is the first policy to get onto the 6 cm curb, and checkpoint 1500
  crossed the 5 cm plank once. But it falls on most runs over the planks,
  usually after landing from the first or second. It also falls without hop
  requests (4–5 of 5), where v2 only stopped. The checkpoints vary too much
  to pick one, so it is not kept. Next would be a longer run with a smaller
  learning rate, landings rewarded explicitly, and planks deep enough to
  land on in training (0.04–0.4 m now).
- **The heading drifts after crossings.** The command is a yaw rate, not a
  heading. `evaluate.py --heading-hold GAIN` models an operator who steers
  back to the scenario's heading.
- **The standard runs:** v1 completes all nine (`eval/comparison.md`); the
  WBC falls in three.
- **Commanded jumps** still give three hops each, with 90–115 mm of
  clearance.
- **Deployment:** like `jump`, its observation includes the two jump inputs,
  which `RlPolicyController` does not provide. It is not exported to ROS.

The next step for curbs is training on step-ups: long, tall platforms, and
more of them, rather than thin planks.

### stand_up: from switched off to balancing

`configs/stand_up.yaml`, `policies/stand_up` (checkpoint 2000 of 3000).

**What switched off looks like.** The description collides only the torso
shell and the two tyre cylinders; the leg links and motor holders have no
collision geometry and the leg joints no limits. Dropped limp, the legs fold
through each other and the body to more than 5 rad. The real legs have no
hard stop either: the links meet each other and the body.
`sandro_rl/collision.py` therefore adds one box per leg body, the oriented
bounding box of its collision-class CAD meshes (their convex hulls have up to
5184 vertices, too many for the GPU contact pipeline), massless, to
`sandro_rl`'s compiled model only. Six body pairs touch throughout a sweep of
the leg motors over ±0.6 rad around the stand pose: each lower link with its
motor holder, and the two lower links at the knee. They share a pin and are
excluded; every other pair collides. Only `stand_up` uses the boxes
(`env.collision.leg_boxes`); the other policies are unchanged.

With the boxes a limp robot folds until the lower links rest on the cranks
(about 1.2 and 1.44 rad) and tips over, front or back.
`python -m sandro_rl.fallen` drops it 1024 times from the stand pose, pitched
by up to ±80°, with some roll, a fore-aft shove and leg noise, and keeps the
852 that come to rest within 3 s (`data/fallen_states.npz`). About 60% lean
15–40° on a folded crank, IMU at 0.19 m. The rest lie at about 83° on the
motor holders, IMU at 0.10–0.13 m.

**Training.**

- **Starts:** 70% of episodes from a random pose of the bank, turned to a
  random heading; the rest standing.
- **No fall termination.** Lying down is where the episode starts. The tilt,
  leg-height and joint-range constraints are off. Stretch and leg split apply
  only once upright (tilt below 0.5 and 0.3 rad): folded flat, the legs are
  stretched, and getting up may brace on one leg. The leg-torque constraint
  is above the 10 Nm cap, which pushing up out of the fold saturates.
- **Rewards:** `upright`, (1 + cos tilt)/2, weight 6. `stand_height`, the IMU
  height from 0.15 m to standing mapped to 0–1, weight 10. Tracking pays only
  once upright (× exp(−(tilt/0.4)²)), so lying still earns nothing for it.
- **Lift assist:** an upward pull on the torso, 30 N while the IMU is below
  half its standing height and fading to 0 at standing height. The curriculum
  halves it at iteration 600 and removes it at 1200.
- **Horizon:** γ 0.995 (2 s at 100 Hz) instead of 0.99, because getting up
  takes seconds.
- **Start:** `flat_level`, with the action noise reset to 0.37 (it was 0.04).
- **Batch:** 4096 environments × 48 steps. The leg boxes' contact buffers do
  not fit 8192 in 16 GB.
- **Drives:** 10 Nm on every drive, as `jump`.

**Attempts:**

| Run | Change | Result |
| --- | --- | --- |
| v1 | From scratch, γ 0.99, `stand_height` = IMU height / standing height, no assist | Never stands: the IMU stays at about 60% of standing height and the noise grows to 1.2. Lying at 30° already earned 93% of `upright` and 58% of `stand_height`, and a 1 s horizon does not see the reward of a get-up that takes 2 s |
| v2 | The lift assist, γ 0.995, `stand_height` from 0.15 m, from `flat_level` with the noise reset | Stands up (below) |

Before either run could learn, three constraints had to change, each of
which held the termination probability at 0.24 of its 0.25 ceiling. A 9.5 Nm
torque limit fired at the 10 Nm cap. The stretch limit fired on legs folded
flat. And a 10.5 Nm limit still fired, because the torque is measured after
the ±15% drive spread.

**Evaluation** (`evaluate.py --scenario stand_up --fallen PITCH`). The robot
starts at the stand pose tipped by PITCH, unpowered for 3 s, and falls limp.
Then the policy engages, with no fall cut-off. The scenario gives 8 s to get
up, then 3 s at 0.4 m/s, 3 s turning at 1 rad/s and 2 s still. Success:
tilt below 0.25 rad with the IMU above 0.27 m at some point, and never above
0.5 rad during the drive phases.

- **Checkpoint choice:** checkpoints 1800–3000 on pitches ±0.3, ±0.8, ±1.4,
  3 seeds each. 1800, 2000, 2200 and 2800 succeed 18 of 18; 2400, 2600 and
  3000 only 14, 9 and 15. The four were then tested on pitches ±0.5, ±1.1,
  ±1.4, 2 seeds, under three latency profiles:

  | Checkpoint | nominal | uart_imu | worst |
  | --- | --- | --- | --- |
  | 1800 | 12/12 | 10/12 | 8/12 |
  | 2000 | 12/12 | 12/12 | 12/12 |
  | 2200 | 12/12 | 12/12 | 12/12 |
  | 2800 | 11/12 | 12/12 | 12/12 |

- **Speed:** from a lean of 23–31° it is up in 0.1 s. From 43–62° it takes
  0.7–1.6 s, and lying at 80–83° 0.4–0.9 s. Nose down, it rocks back onto
  the wheels and extends the legs. Nose up, it braces on one leg ahead of
  the other before standing (`eval/stand_up_*_frames.png`, `stand_up_front.mp4`,
  `stand_up_back.mp4`).
- **Once up**, it holds 6–7° of tilt at most while driving and turning,
  with the IMU at 0.32 m. The legs stay within 3 mm of each other fore and
  aft (15 mm in the turn, from the roll).
- **Torque:** the push up reaches the 10 Nm cap on single drives, above the
  controller's 3 Nm leg limit. On the robot this needs `jump`'s higher
  limits.
- **The standard runs** from standing: it completes all nine
  (`eval/comparison.md`); the WBC falls in three.
- **Not checked:** stand-ups on slopes or obstacles. And the boxes are a
  coarse stand-in for the CAD links. Where the robot really comes to rest
  depends on them, so a photo or a measurement of the real switched-off pose
  would be worth comparing against the bank.

### Wheel drive-train lag: the 7.5 Hz ringing on the robot

On the robot, `flat_level` rang at 7.4–7.5 Hz: both wheels in phase, actions
±0.7, 2.3 Nm RMS per wheel (docs/HANDOFF_flat_level_real.md). Body pitch
acceleration lags the reported wheel torque by 24–25 ms, and the IMU lags
the encoders by only 9 ms, so the lag is in the wheel drive train (backlash
and compliance), not in sensing. Training had randomised only 0.5–3 ms of
command delay.

- **Model:** `randomization.drives.wheel_lag_s` (base.yaml, 10–80 ms per
  episode; `nominal_wheel_lag_s` 40 ms) is a first-order lag on the wheel
  actuator torque at the physics rate. 50 ms of it is 67° of phase, 25 ms,
  at 7.5 Hz, which matches the robot. A backlash deadzone is not modelled.
- **Reproduced:** `evaluate.py --lag-sweep` runs hardware, default and push
  at 0, 35, 50 and 80 ms (`eval/lag_sweep.md`; the pre-refit sweep is
  `eval/lag_sweep_before.md`). `flat_level` rings at 7–10 Hz, 1.2–1.4 Nm,
  and falls at 80 ms; `agile_terrain` rings at 5–8.5 Hz, 1.1–1.6 Nm;
  `flat_tracking` falls at 35 ms. The 10 Nm policies (`jump`,
  `step_climb`) do not ring, and `stand_up` wobbles at 3.8 Hz.
- **Fine-tune** (`scripts/refit_lag.sh`, `sandro_rl/refit.py`): resume
  each policy with the final stage of its curriculum from iteration 0, the
  lag at 0–30 ms for 300 iterations and then 10–80 ms, 1000 iterations,
  learning rate 3e-4, and `train.resume_log_std` −1.2. The resumed action
  std (about 0.04) otherwise makes the first updates' KL 100× too large: a
  direct resume onto the full lag fell 16 times per 1000 steps.
  `flat_level_real` (`configs/flat_level_real.yaml`, 1500 iterations) also
  doubles the `action_rate` and `action_accel` weights.
  `scripts/package_refit.sh` replaces `policies/<name>` by the refit and
  re-evaluates it; the refit's curves are `*_lag`.
- **Comparison:** `--compare --sim wheel_lag=0.04` runs the policy with
  40 ms of lag and the WBC without (sandro_sim has no lag model). Each
  refit at 40 ms against the original at 0 ms (its own conditions), mean
  over phases:

  | Policy | Ringing at 35–80 ms | At 40 ms against the original at 0 ms |
  | --- | --- | --- |
  | `flat_level_real` | none (0.14–0.32 Nm, 5–15 Hz share ≤ 0.18) | Velocity and yaw errors within 10 %, pitch the same. Completes all 9 |
  | `flat_tracking` | none (0.13–0.32 Nm) | Velocity and yaw errors within 10 %; pitch RMS 0.04 → 0.065 rad in the worst profile. Completes all 9 |
  | `agile_terrain` | none (0.13–0.33 Nm) | Better: pitch RMS 30–70 % lower; worst profile velocity error 0.21 → 0.07 m/s, wheel torque 1.8 → 0.56 Nm. Same course (planks up to 20 mm). Roll 0.24 rad for 0.3 commanded (0.27 before) |
  | `jump` | none | Hops 86–116 mm. Lands every hop on 5 of 5 seeds with the UART IMU, where the original at 40 ms falls on 4. Both fall on 5 of 5 in the worst profile. Steady driving 10–50 % worse |
  | `step_climb` | none | Against the original at 40 ms: 5 of 20 planks either way, 1 fall in 5 instead of 2, a third to a quarter of the wheel torque under slow sensing. Yaw error 0.024 → 0.039 rad/s at nominal latency |
  | `stand_up` (checkpoint 500) | none | Up and staying up in 18 of 18 falls at 40 and 80 ms, and with the UART IMU and worst profiles at 40 ms. Once up, against the original at 40 ms: wheel torque 3–5 → 0.6–1.0 Nm, velocity error 0.5–0.67 → 0.08–0.12 m/s. Holds the leg height 16 mm off (2 mm before) |

- **`stand_up` checkpoints:** the stand-ups erode with more training under
  the full lag. On one seed per fall, checkpoint 400 succeeds 6 of 6, 600 5,
  and 700–1000 4: the 62° nose-up fall fails. Checkpoint 500 is kept.
- **Zero lag:** `flat_tracking` chatters at 50 Hz (1.0 Nm on one wheel) at
  exactly 0 ms, which the drive train cannot have; at 5 ms it is clean.
- **Deploy:** `export_ros policies/flat_level_real:rl_flat_level
  policies/agile_terrain:rl_agile_terrain` is done. Both were trained at
  wheel kd 0.4 with no wheel filter, so `wheel_kd_nm_s_rad: 0.4` and
  `wheel_filter_hz: 0`. `recordings/real_overrides_kd025_f4.yaml` (kd 0.25,
  4 Hz) was a stopgap; its filter adds lag of its own.

## 9. Deployment sketch (not executed; the owner's decision)

This is a `sandro_controllers` controller plugin, `RlPolicyController`, that
replaces `whole_body_controller` and claims the same interfaces:

- **State interfaces:**
  - IMU orientation and angular velocity;
  - per joint, position and velocity.
- **Command interfaces:**
  - per leg joint, `position`, `velocity`, `kp`, `kd`, `effort` (the MIT
    interfaces the hardware plugin already exports, S2R l.400–403);
  - per wheel, `velocity` and `kd` in velocity mode, or `effort` in torque
    mode.

`policy.json` holds everything the controller needs:

- the observation layout, scales and history;
- the normalisation, which is baked into the ONNX graph;
- the action mapping, `stand_q`, gains and torque limits;
- the command shaping;
- the IMU offset correction;
- the rates;
- the model fingerprint.

The controller runs as follows:

- **Rate:** `update()` at 300 Hz (controllers.yaml `update_rate`). On every
  3rd cycle it builds the frame, runs inference and writes 6 MIT frames;
  otherwise it holds the frames.
- **Inference:** onnxruntime's C++ API, single-threaded, with the session
  created in `on_configure`. The actor has about 125k parameters. Its time
  per inference on the Raspberry Pi 5 is not measured here and must be
  measured before deployment. A missed deadline holds the previous frame.
  The model input and output sizes are checked against `policy.json` at
  configure.
- **Real-time safety:** no allocation in `update()`; preallocated tensors.

Safety fallbacks reuse the WBC's parameters from controllers.yaml `safety`:

- `fall_angle_rad` (1.0): beyond it, zero kp and kd 0.5 on the legs,
  zero wheel torque, latched until re-activation;
- `imu_timeout_s` (0.15) and `command_timeout_s` (0.3): an IMU timeout
  triggers the same fallback; a command timeout ramps the command to zero;
- `ramp_s` (0.5) on activation: the gains ramp from the measured pose;
- the hardware plugin's MIT frame-bias check stays in charge (S2R l.436–437).

A non-finite network output also triggers the fallback.

The `velocity` wheel mode needs the MIT `velocity` and `kd` command
interfaces on the wheel drives. The plugin exports them for all six joints
(S2R l.400–403), so this is a configuration change only.

## 10. Assumptions and open issues

- **Drive speed limit.** No wheel speed limit is documented. The MIT frame
  encodes ±65 rad/s (the GIM6010 MIT range). 1 m/s needs 14.9 rad/s at the
  loaded 0.0672 m tyre radius, and the policies use at most 20 rad/s.
- **The 0.31–0.46 velocity gain of one left drive** (S2R l.248, l.283) is
  outside the randomised 0.75–1.05. A policy that relies on leg velocity
  would be hurt by that fault. Check that drive first, as S2R advises.
- **IMU rate on SPI** is unmeasured. Both 30 Hz and 200 Hz are in training
  and in the evaluation profiles.
- **Encoder noise, gyro bias and kp scale** are assumptions (section 5).
- **Sim-to-sim gap.** The GPU environment and the CPU evaluation share the
  MJCF and the observation code (tested), but differ in two ways:
  - the physics is computed by different engines (section 3 gives the
    measured differences);
  - the evaluation runs the full `DelayLine`/`DriveBus` emulation, while
    training uses its batched equivalent.

  Every result in sections 7–8 is from the CPU evaluation, not from
  training.
- **Solver iteration limit.** MuJoCo Warp prints "solver iterations limit
  reached" during training. That happened 140 times in the 1000 iterations
  of `flat_tracking` and 233 times in the 1500 of `agile_obstacles`, each
  time in some of the 8192 worlds. I did not trace which states cause it
  (likely falls with many body contacts). The CPU evaluation, at the MJCF's
  own solver settings, is what the results rest on.
- **A world's simulation can diverge** (`agile_terrain_v0`, iteration
  1220). The guard in `env.step` contains it (section 8); the cause, one of
  pushes, torque kicks or ramp contacts, was not traced.
- **`agile_terrain`'s height range** is 0.12–0.18 m in practice, against
  0.09–0.19 m commanded (section 8). The next things to try:
  - a height-bin breakdown of the training error, to see whether low
    heights fail on flat ground or only on terrain;
  - a curriculum that widens the height range last;
  - the leg torque and wheel torque terms' cost at low heights;
  - a heavier height weight.
- **Roll feasibility** uses the per-leg range 0.07–0.195 m and the
  track width from the MJCF. The bounds are mine, chosen inside the
  kinematic reach; they are not measured limits.
- **Hardware data:** the owner's `flat_level` deployment rang at 7.5 Hz
  (section 8, wheel drive-train lag). The lag refits are untested on the
  robot. The 20 % agreement criterion of S2R §2 is the test to apply first,
  with a short, gentle sequence. The lag model is first-order only; if the
  refits still ring, a backlash deadzone is the next thing to model.

## 11. Proposed changes to the existing packages (not made)

1. **`closed_loop.cpp` `Sim::truth`**: compute the truth speed at the axle
   midpoint in the heading frame, as `evaluate.py` does with
   `diag_truth_forward_m_s`. At the torso origin it includes ω × 0.35 m
   while turning, and pitch motion as well (section 7).
2. **`closed_loop.py check`**: the `default/uart_imu` gate fails today
   (S2R l.518–519). Before raising `balance.effort_weights.wheel_torque`, a
   SPI IMU-rate measurement is the cheaper fix (S2R l.493–495).
3. **`sandro_controllers`**: add the `RlPolicyController` of section 9 as a
   separate plugin, so the WBC stays untouched and selectable with
   `controller:=`.
4. **`sandro.launch.py`**: `controller:=rl_policy policy_dir:=...` would
   load `policy.json`. The launch's latency arguments already cover the
   simulation side.
5. **`sync_model.py`**: run `sandro_rl.consistency` after `sync`, or
   document it as the follow-up step, so model changes surface as a failing
   check rather than a silently changed policy.
6. **`controllers.yaml` `drive` limits** (0.5 m/s, 1.5 rad/s) cap what the
   policy can be commanded through the WBC's shaping. `agile_obstacles` is
   trained to 1.0 m/s and 3 rad/s. Deploying it at that speed needs those
   limits raised for the RL controller only.
7. **`sim_identified.yaml` `imu_mount.roll_offset_rad`**: still the UART
   IMU's −0.049, while the robot overrides give the SPI6 mounting as
   +0.016. Its own comment says the simulated IMU should be rotated by the
   overrides' amount. The policies are unaffected either way, because they
   correct by the simulated mount and the robot's mount reaches them through
   the `rl_*` overrides. Matching it would make the WBC's simulation hold the
   same horizon as the robot.
8. **`sandro_description` collision geometry**: only the torso shell and
   the tyres collide. Leg-link collision shapes (`sandro_rl/collision.py`
   fits boxes to the CAD meshes) would make falls and the switched-off pose
   physical in every simulation, not only in `stand_up`.
9. **Starting a policy lying down** (`stand_up`): `RlPolicyController` would
   need a mode that engages with the robot fallen. The WBC's fall cut-off
   (`safety.fall_angle_rad`) must not apply until the policy is upright. The
   folded legs sit at up to 2.2 rad, outside the ±2.09 rad joint range.
   Pushing up takes the 10 Nm drive limits, against 3 Nm today.
